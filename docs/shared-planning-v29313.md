# v293.13 販売予定・船便・発注残の初回共有

発注・船積みの判定に必要な情報を段階的に共有するための土台。初回だけバックアップから予定情報をコピーする。現在庫・売上履歴・取引履歴はこのAPIで変更しない。過去の船便到着を再入庫しない。

## 今回できること

- 全データバックアップから販売予定、船便、船積振分け、倉庫振分け、入荷反映済み記録、商品別発注残だけを抽出する。
- 管理者が送信して件数を確認する。確認だけでは保存しない。
- 明示的な確認後に初回共有する。登録済みの共有予定は上書きしない。同じ管理者・同じ内容・同じ操作番号の再送は保存済み結果を返す。
- 未確認の操作はパス別に保存し、自動送信せず、同じ管理者が再確認する。トークンを保存しない。
- 作業者は登録された情報の共有状況を閲覧できる。未共有は「未共有」と表示し、0件と区別する。
- 不明な発注残はnullで保持し、0と解釈しない。商品コードと船便IDの対応不明・重複IDは停止する。

## 残る作業

この版では発注必要数・船積必要数を計算しない。販売実績の共有、既存の月平均・季節補正・取引先除外処理の接続、共有予定の編集・更新、共有船便の確定・入荷処理が残る。初回共有後に端末内で変更した予定は自動同期しない。画面も初回共有時点の内容と明記する。

## 配置

1. 既存DBを非公開領域にバックアップする。
2. `server/tools/inventory-v29313-setup.php` と `server/migrations/005-shared-planning.sql` を非公開フォルダーへ置く。SQLの配置名は `inventory-v29313.sql`。
3. CLIでsetup.php migrateを実行し `planning_table_ready:true` を確認する。既存在庫は変更しない。
4. `shared-planning-auth.php` と `shared-planning-service.php` を既存inventory APIと同じ場所へ置き構文確認する。
5. 検証版で架空JSONを件数確認→初回共有→再送→別ユーザー閲覧の順に確認する。共有先にはテスト初期化が残るため、実データ初期化前に検証DBを使うか、別の検証用テーブルを準備する。本番の予定領域を架空データで初期化しない。
6. 本番の初回共有は実際の最新バックアップで件数確認後に管理者が実行する。公開はユーザー承認後。

## 検証

Node: 投影対象、売上・在庫の除外、不明な発注残、確認前書き込み禁止、通信途絶後の再読込・同じ操作番号での再確認、アカウント変更、保存領域不使用時、ログアウト・同時クリックを検証。

CIの使い捨てDB: 管理者権限、未共有状態、プレビュー非保存、再送・他ユーザー拒否、上書き拒否、識別子重複・数量・商品と船便の参照、在庫・履歴の不変、保存失敗ロールバックを検証。
